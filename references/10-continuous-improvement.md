# 10. 持续改进（每次使用后的必跑步骤）

## 目标
复盘应提升下次研究质量，而非积累聊天全文。收集**可复用的一般性错误机制**，保存来源及适用边界，让后续会话读取。经验分成事实错误、来源问题、口径问题、结构写作、模型假设、交付偏差六类。

## 会话结束协议（POST-SESSION）
1. 回顾本轮用户的明确纠错、反复要求和得到确认的研究结论。
2. 判断是否**可泛化**：例如「原药竞品要比较同用途的不同有效成分，不要把厂家混为竞品」可转规则；某公司某期价格具体金额应保留在项目工作底稿，不进入全球规则。
3. 为每条拟沉淀规则填写 `templates/feedback.json`：问题、纠错、未来规则、适用场景、原始依据类型、信心、用户是否明确确认、影响模块。
4. 仅提炼必要抽象规则。不上传会话全文、不上传保密客户与会议原文、不上传受版权保护的大段内容。
5. 若 GitHub 工具可写 `FR`：使用 GitHub `create_issue` 提交带 `fr-feedback` 标签的 JSON 问题单。GitHub Actions 随后创建修改 PR。若无法自动添加标签，可先创建 Issue 再加标签。
6. 若当前无法访问 GitHub：在本地运行 `python scripts/ingest_feedback.py --file feedback.json --repo .`，保留本地变更供后续同步。
7. 若此轮没有可泛化的新规则，输出 no-op，不为完成流程制造虚假的学习。

## 自动化边界
- ChatGPT 分享链接或其他私聊内容**不会自动出现在 GitHub**。使用此 Skill 的会话代理必须主动提交结构化反馈；只有本步骤完成才触发后台 PR。
- 默认保留审查，GitHub Actions **自动修改候选知识文件并开 PR**，而不是无人审核直接覆写核心规则。
- **不因用户表达喜好就篡改客观数据、合规要求或研究方法的事实部分。** 用户明确确认的风格和工作流偏好可优先提议。
- 当规则与研究材料冲突，先区分适用上下文，必要时记录反例或回滚。

## 优先级与升级
1. 可证实的用户纠错 → 高优先级候选。
2. 多次重复的一致经验 → 高优先级候选。
3. 一次性偏好/无法核查观点 → 标为「试行」并附上下文，默认不纳入 accepted_rules。
4. 对引用标准、合规、估值公式等基础规则进行重大修改时，必须人工复核和记录动机。

## 防止退化
- 每条规则必须短、可执行、可判定，包含适用范围和典型反例。
- 保持一个主规则文件 `memory/accepted_rules.md`，追加候选不得覆盖既有内容。
- 重复内容合并；相互矛盾时走PR解释冲突，不直接追加相反规则。
- 维护 `CHANGELOG.md` 和回归测试，至少月度清理过时规则。
